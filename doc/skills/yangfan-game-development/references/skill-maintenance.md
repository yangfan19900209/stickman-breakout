# 杨帆游戏开发体系的自动维护

## 默认执行时机

在使用本技能完成一轮游戏开发、问题修复、素材接入或验证后，将维护作为同一任务的收尾工作。用户已要求自动更新，无需再提议“是否整理为 skill”。无需后台定时任务，也不在没有新任务或新证据时自行修改。

先完成本轮实际改动和必要验证，再决定哪些结论值得保留。若仍有阻塞，只提炼已确认的部分；未证实的猜想保留在任务记录，不能变成确定性指导。

## 更新什么

| 本轮发现 | 维护方式 |
| --- | --- |
| 可复现问题及已验证修复 | 提炼触发条件、原因、有效修复、关键回归，归入对应参考文件 |
| 新的可复用设计方法 | 说明适用场景、取舍和如何验证，不复制当前关卡全部数值 |
| 成功的素材生成/接入方法 | 更新提示词或资源契约，记录实际尺寸、锚点、透明度及验证边界 |
| 组合专项技能后验证有效的方法 | 总结采用理由、来源技能、引擎/平台条件、效果与局限，归入相关参考；不整篇复制来源技能 |
| 新引擎、新玩法或新技能的适用经验 | 将通用方法与引擎 API 分开；必要时新增专项参考并补入口，不将单引擎结论扩成通则 |
| 已有指导失效、错误或重复 | 修改或删除原条目，保留必要例外，避免在文末叠加相反规则 |
| 一次性调参、截图、版本进度 | 放项目文档、资源清单或报告，仅在有迁移价值时链接为实例 |
| 只是又一次证明旧方法可用 | 通常无需改动技能，不增加重复条目 |

按需要更新既有分类：技能协作、物理与战斗、节奏与呈现、资源流程、素材提示词、性能、验证与交付。新方向积累出独立方法后再新增参考文件并补入口。`SKILL.md` 只保留入口和跨任务规则，项目特例放 `project-examples.md`；不要把主入口写成完整开发日志。

## 总结到修正的闭环

1. 从本轮实现和验证中区分“实际采用且有效”“被验证否定”“尚未验证”，连同来源技能和适用条件整理；未验证内容只进入项目任务记录。
2. 查找本体系是否已有对应指导：已有则补充条件或直接修正；确为新增方法再归档，重复证明不新增条目。来源技能出现错误时，在本体系保留经过验证的修正与边界，不擅自修改其安装文件。
3. 修正与删除同时检查调用入口、交叉引用和可能受影响的其他引擎场景，避免保留相互矛盾的规则。技能名称与路径变更时，同步修改当前默认入口、界面元数据和示例命令；历史证据保留其原版本归属。
4. 按下文校验、合并并同步；交付只概述实质变化和未完成部分。维护是本轮工作的收尾，不创建定时任务。

## 维护源与同步

1. 当前仓库已有 `doc/skills/yangfan-game-development/` 时，以它为维护源。安装目录为 `$CODEX_HOME/skills/yangfan-game-development/`，未配置 `CODEX_HOME` 时为 `~/.codex/skills/yangfan-game-development/`。
2. 开始修改前比较两处内容；若安装副本含其他任务留下的有效改动，先合并回项目源。已有同步哈希记录可帮助区分新变化，不能盲目用旧副本覆盖新经验。
3. 在维护源完成改动和验证后，将对应修改同步到安装目录，核对文件集合与 SHA-256。生成相对路径清单前先统一路径形式，尤其是 Windows 的短路径与长路径；不要对不同形式的路径直接按字符串长度截取。删除过时文件前检查引用和目标路径；不要为了“同步”删除整个 skills 目录或无关文件。
4. 当前仓库没有项目副本时，在本次加载的安装目录维护通用技能；不通过旧的绝对路径修改另一个游戏仓库，也不为了维护而自动创建重复技能。项目特例继续保留在当前项目文档。
5. 写入权限遵循实际工具要求，已有维护授权无需重复询问。若权限或冲突确实阻止同步，保留已完成的修改并准确说明未同步部分，不声称两份已一致。

这是“杨帆游戏开发体系”及其必要入口的持续维护授权，不扩展为其他技能、用户全局记忆、无关项目或游戏发布的修改授权。

## 维护后检查

- 用可用的 `skill-creator` 官方 `quick_validate.py` 检查格式；检查引用文件、自动调用设置及提示词中的技能名。
- 仅文字或配置变化时检查内容与链接，不重跑无关的游戏测试。新增或修改辅助脚本时，运行能验证实际行为的用例。
- 同步后检查文件集合及内容哈希。更新项目已有的技能验证记录时，区分本次重跑与沿用的历史证据，不能把旧测试标成本次重新运行。
- 交付时用一句话说明技能新增/修正了什么以及同步状态。没有实质更新时可以只报告开发结果，不必输出空的维护清单。
