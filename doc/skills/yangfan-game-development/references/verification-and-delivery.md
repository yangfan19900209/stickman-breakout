# 验证与交付

## 按行为选择证据

| 层级 | 能证明什么 | 不能据此宣称什么 |
| --- | --- | --- |
| 类型检查/编译 | 接口和构建链可用 | 游戏可玩、画面正确 |
| 模拟测试 | 碰撞、时序、资源消费、状态恢复 | 实际渲染/触控正确 |
| 浏览器运行 | 当前浏览器中的画面与输入链 | 微信运行或手机硬件能力 |
| 微信开发者工具 | 微信包加载、API 兼容和工具内画面 | 真机帧率、真实多指和震动 |
| 目标设备 | 该设备上的触摸、性能、显示与硬件反馈 | 未测试设备或版本全部兼容 |

测试范围匹配修改风险。简单文档调整不必重跑全游戏；涉及物理、状态机或资源消费的改动应包含行为回归。通过后不重复扩大测试，除非又有修改或新证据暴露问题。

## 让输入经过真实链路

浏览器自动化通过键盘、鼠标或触摸事件完成动作，使用只读快照采集玩家、敌人、弹体、镜头与时间线状态。不要靠调试接口直接设血量、击杀 Boss 或把玩家传送到目标点，再宣称完整通关通过。

模型单元测试可以直接创建必要状态以隔离规则；报告中区分这种覆盖与真实输入流程。保留可以复现的起点、输入顺序、视口和随机种子（若项目支持）。

后撤与换边的验收要遵守当前瞄准规则：若持续开火会保留朝向用于横移，后撤停火后应通过正常输入转身再开火，不要让自动策略一直背对 Boss 射空，也不能把该策略失败直接归为伤害不足。角度判断要遵守实际范围，例如 `atan2` 的向下锁线可能是负角；记录面向、瞄准目标、真实命中和受伤时刻，区分控制策略错误与游戏规则缺陷。

Creator 3.8.8 的浏览器输入层会把鼠标操作模拟为触摸事件；同一控件同时处理全局鼠标与触摸可能执行两次动作。采用单一输入路径，或在需要分别处理时按事件来源去重。用真实页面的一次点击检查奖励、购买、吃药和菜单跳转，而不只检查键盘操作。触屏自动化也要按实际设计分辨率与等比缩放后的内容区映射坐标，不能直接把包含留白的整个 canvas 矩形当作设计区域。

固定浏览器时钟后按可控时间推进，在引擎初始化之前安装时钟；初始化后再切换计时基准可能使引擎获得异常时间差，表现为不移动或错误累积。暂停演出时确认模拟时间未变，恢复后事件只触发一次。不要用超长真实等待代替可控推进。

时钟可能作用于整个浏览器上下文。多用例需要独立计时时使用独立上下文，不在已冻结的上下文中反复安装；刷新页面测试应先恢复时间，让引擎初始化和资源调度完成，再冻结并推进。等待条件超时时先区分应用错误与测试时钟停住，不为通过自动化而修改游戏时序。

## 针对常见改动的回归

| 改动 | 有价值的验证 |
| --- | --- |
| 箱体落地 | 完整箱/残骸/碎片/掉落物；支撑消失和多层平台 |
| 近战保护弹药 | 同一次长按穿过挥刀恢复、箱体销毁和自动拾取 |
| 火箭枪口 | 左右/向上/空中；自由飞行与被真实平台遮挡分别检查 |
| 补给 | 满血不吃、缺血触发、附近去重、生成失败可重试、重开重置 |
| 关卡延长 | 实际路线能走通、两次 Boss 之间有玩法、计时与压力分布 |
| Boss 演出 | 同时死亡边界、事件跳帧、暂停恢复、残留闪光、结果按钮和重开 |
| 触控 | 多指同时、短按、取消、失焦、横竖切换、边缘安全区 |
| 图集更新 | 源文件、帧范围、动作选择、镜像挂点、实际视口截图 |

断言外还要看图。一次胜利流程的逻辑测试可以全通过，画面却仍卡着最后一枪的枪口闪光；发现后补充具体断言并重新运行受影响用例。

## 用户认可版本的可恢复锚点

用户明确认可某一版本或某一关时，记录认可范围与时间，不扩大为所有章节、所有设备均已验收。下一轮修改前保留实际工作区源码、运行资源、配置/依赖锁与当前构建，记录逐文件和归档 SHA-256，并重新读取归档验证内容。脏工作区的 Git HEAD 往往落后，单独记提交号不足以恢复体验。

给锚点稳定 ID、文档入口和恢复方法；已有锚点拒绝覆盖。恢复到新的空目录，避免覆盖后续有效改动。排除缓存、安装目录和秘密凭据；保存必要生成来源与原版本证据。对认可的移动、几何、敌人、补给和美术建立改前/改后核对，获准变动的显示反馈单独列出。历史证据不改名为本轮证据，当前修改依然需要相应验证。

## 截图与证据归属

截图命名包含版本、平台、场景或关键时刻。记录来源环境和视口，不把浏览器 PNG 改名成微信截图。用户要求“每类三张”意味着每个类别都有三张，并核对每张实际内容。

关键截图至少覆盖被改动的状态，避免只展示漂亮的首页。动作问题需要发射/命中/恢复的连续关键时刻；时间线问题需要坍塌、近景、结算与重开。

硬件 API 的模拟调用次数只证明调用请求。真正震动、浏览器系统 UI 行为和手机触摸响应需要目标环境运行，未测就明确写未测。

## 微信原生社区入口与覆盖层

接入游戏圈首页前，区分“当前游戏社区首页”和“指定帖子/话题”。核对当时的微信官方 API：`wx.createGameClubButton` 的 `openlink` 为可选项时，可直接使用原生首页按钮，不应把专属链接误当作所有接入方式的前置条件；指定页面才按对应接口核验 openlink。`show()` 只是显示按钮，不代表打开社区，原生点击回调也不等于页面加载成功。参考 [微信官方小游戏类型定义](https://github.com/wechat-miniprogram/minigame-api-typings/blob/master/types/wx/lib.wx.api.d.ts)，升级时重新核对。

原生覆盖层有独立生命周期：使用窗口逻辑像素，将引擎按钮实际世界边界转换成左上角坐标，不能重复乘 DPR；在菜单可见时显示，在战斗、过场加载、竖屏提示及后台隐藏。实例和监听仅创建一次，布局变化再更新；销毁时解绑同一监听并清理组件。兼容入口需避免同一原生点击透传后误报错误；创建失败不能按帧无限重试。离开与返回时清除残留输入，不能因恢复原生页面而擅自解除玩家暂停。

验证覆盖旧接口缺失、创建失败、不同 DPR/窗口、菜单与战斗切换、前后台、横竖屏和销毁后的迟到回调。浏览器中的原生组件模拟只能证明菜单/生命周期集成，真实社区打开、平台资格与设备行为仍需微信环境确认。资源异步加载完成前不要冻结测试时钟后直接等待依赖帧推进的状态，否则可能制造假超时。

游戏圈要与游戏图片按钮统一风格时，可保留引擎已有的生成底板和文字，原生 `type: "text"` 覆盖层使用空文字、透明背景与零边框，仅承担原生点击。图标选项仅对 image 类型有效。两层始终共享同一可见边界、背景隐藏和销毁时机；同时检查首页与暂停菜单、文字粗细和新增按钮旁的旧提示，避免修首页却遗漏暂停页。透明层的浏览器模拟通过仍不能代替微信真机的透明合成确认。

## 微信转发入口

游戏内主动分享与右上角菜单转发分别接入 `wx.shareAppMessage`、`wx.showShareMenu` / `wx.onShareAppMessage`，共用公开卡片信息，不把本地跳关参数带入分享。按当时官方定义核验支持范围；默认分享图在当前 API 与指南中的描述并不一致，普通分享应真机确认默认效果，要求稳定战绩卡时显式指定图片并复用已有美术，不承诺一定自动截图。监听只注册一次，销毁时解绑同一函数；请求分享和前后台切换均清理输入，返回后保持原来的暂停状态。只记录“已请求”，不能将返回前台、停留时长或接口未抛错当成发送成功；用户明确采用请求即得的产品规则时，按请求验证并说明取消也获得，不能宣称验证了送达。测试使用模拟接收方验证请求和生命周期，不实际向他人发送消息；真实分享面板、卡片及收件人打开仍由微信环境确认。好友榜、定向邀请、群榜与开放数据域的额外约束见[微信社交接入](wechat-social.md)。

## Creator 构建与包体

复用项目现有构建脚本，先核实引擎版本、配置与可执行文件。Windows 后台启动辅助程序时使用隐藏窗口，保存日志与退出状态。

一些历史引擎/脚本组合有特殊成功退出码；只在当前环境已证实的情况下兼容。结合构建完成日志和必需入口文件判断结果，不把未知非零码全部视为成功。本项目 Creator 3.8.8 的退出码 36 处理只是实例。

手工生成场景时，自定义脚本组件的 `__type__` 应使用引擎实际注册的 class ID；3.8.8 常见的是 23 位压缩 UUID，不能直接拿脚本 `.meta` 的 36 位 UUID 替代。可与生成脚本中 `_RF.push` 的注册 ID 核对。已实测缺失脚本时构建仍可能返回 36，因此还要检查 Missing class / missing or invalid 日志，并在最终包中确认初始化完成。

微信/小游戏资源限制可能变化。分别测量主包、分包和总体积，对照当前目标平台规则；不能拿总包数字代替主包数字，也不能把旧项目限额当成永久标准。采用引擎分包机制时验证启动预载路径，确保游戏首次用到资源时已经可用。

Creator 的资源包配置随版本变化，应读取本机类型定义和实际构建结果。3.8.8 本地验证使用 `源码/settings/v2/packages/builder.json` 的 `bundleConfig.custom` 预设，并由目录 `.meta` 的 `bundleConfigID` 引用。`custom` 是以预设 ID 为键的对象，不是数组；预设包含 `displayName` 和 `configs`。小游戏配置位于 `configs.miniGame`，使用 `configMode: "overwrite"`，并在 `preferredOptions` 与 `overwriteSettings.wechatgame` 内设置 `compressionType: "subpackage"`、`isRemote: false`；Web 可使用 `configs.web` 的 `configMode: "auto"` 与 `merge_dep`。旧 `.meta` 或 CLI `bundleConfigs` 中单独填写 `compressionType` 不足以证明配置生效。CLI 的 `bundleConfigs` 还是包含资源包的选择列表，只写新章节可能排除原 `resources` 包；不要为压缩配置随意缩小该列表。参考[官方资源包预设说明](https://docs.cocos.com/creator/3.8/manual/en/editor/project/#bundle-config)。

构建退出成功后检查 `game.json` 的分包项、分包目录、引擎 settings、必需资源 paths 和实际字节数；体积骤减也可能是漏打包。章节分包结构检查只能证明构建结果，微信加载和设备内存仍需目标环境验证。浏览器整关计时应保存各次结果并说明自动操作策略；单次时间接近不能代表人类游玩时长已经定案。

构建输出更新后，再运行针对该输出的浏览器验证。交付记录关联源文件版本或 SHA、构建日志、资源 SHA、测试启动时间和截图路径；最后一次源码修改之后的结果才算本次证据。

如果只有文档变化，清楚说明游戏包没有重新生成；如果游戏代码/资源变化，则不要沿用之前的旧构建和旧截图冒充最终结果。

## 完成交付

保留失败证据与最终有效证据的区别。摘要写“已实现什么、在哪些环境验证、还有哪些具体未验证项”，不用漫长命令清单替代结论。

构建、上传、发布、推送 Git 是不同动作。遵循当前用户授权范围，不能因为本地验证通过就自动对外发布；已有明确发布授权时继续完成，不重复索取确认。

版本交付同时核对包元数据、游戏内标记、浏览器缓存版本与上传说明；上传脚本读取本版本的说明，不沿用历史硬编码文案。用于提交的目录应从已验证的最终构建复制，记录逐文件与压缩包哈希并解包回验，避免后续构建覆盖用户准备上传的版本。更新说明只描述已开放内容，闭锁的试验章节不写成上线功能；本地包、上传回执和线上发布状态分别记录。

源码、创作来源、运营材料、计划、进度与固定交付各有用途。目录调整先核对引擎根目录和发布配置，详细方法见[工程整理与清理](project-organization.md)。本项目当前布局见[实例索引](project-examples.md)；其他项目先沿用其实际约定，不强制相同命名。

## 并行迭代的构建归属

同一 Creator 工程的导入缓存、构建目录和日志会被多任务共享。构建应串行化；等待超时或共享进程未退出时，不结束其他任务的进程。可用已经校验的构建输入副本在独立工程目录生成另一平台产物，保留独立日志并核对同一输入 SHA。

在开始构建与固定产物前核对运行代码、资源和配置的文件集合与哈希；代码在构建期间变化时，不把该包与当前源码直接对应。复制最终包后逐文件复核，在独立本地地址测试固定副本，并让报告、截图和压缩包指向同一份内容。后续共享工程继续变化不应覆盖已经完成的交付。
