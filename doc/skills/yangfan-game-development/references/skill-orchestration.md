# 已安装游戏开发技能协作

## 发现与选择

本体系可以组合使用所有当前已安装且可访问的游戏开发技能，包括之后安装或更名的技能。下表仅提供选择方向，不是固定目录或白名单；无需先把每个技能登记进本体系才能使用。

1. 先确认当前任务的引擎与实际版本、玩法类型、目标平台、需要改变的行为以及已有稳定实现。
2. 以当前会话可用技能列表为入口，根据名称与描述筛选候选；按目录提供的路径、别名根目录或提供方读取所选 `SKILL.md`。命名空间和嵌套目录中的技能同样可用，不假定都位于 `skills/<名称>/`。
3. 列表缺项或路径失效时，再定向查找当前项目的技能目录、`$CODEX_HOME/skills`（未设置时用 `~/.codex/skills`）；文件系统可用 `rg --files <目录> -g SKILL.md`。插件或云端技能通过当前提供方发现和读取，不把远程标识当成本地路径，也不扫描整个磁盘。
4. 读取与任务有关的技能正文及必要参考，确认它依赖的工具、代码和平台确实可用。技能文件存在不代表相应编辑器、服务或发布权限已经具备；缺少依赖时完成可执行部分并如实说明。
5. 将选定方法落到当前项目的真实入口，再实施与验证。只有复杂组合、新技能复查或有争议的选择需要在项目记录中列出技能、用途和适用性证据；不为小修建立全量审计表。

## 按问题组合

| 当前任务 | 选择方向与已安装技能示例 |
| --- | --- |
| 规划原型、判断玩法与技术路线 | `prototype-fast`、`game-jam`；需要综合选型时参考 `router`、`game-studio` |
| 使用现有引擎开发、编辑器集成、语言与构建 | 匹配实际引擎的 `unity-*`、`godot-*`、`unreal-*`、`roblox-*`；Cocos 可读取本体系保留的专项参考 |
| Web 或轻量引擎开发与渲染 | `phaser-*`、`pixijs-rendering`、`threejs-*`、`bevy-ecs`、`defold-core`、`ebitengine-game`、`love2d-core`、`pygame-core` |
| 具体游戏类型与核心循环 | `platformer`、`fps-shooter`、`card-game`、`puzzle`、`rpg`、`roguelike`、`survival-crafting`、`tower-defense`、`visual-novel` |
| 输入、镜头、运动与操作反馈 | `input-systems`、`camera-systems`、`physics-tuning`、`game-feel`，再配合当前引擎的相关技能 |
| 敌人决策、关卡与生成内容 | `game-ai`、`ai-behavior-trees-utility-ai`、`level-design`、`procedural-gen`；引擎导航或行为树技能按需补充 |
| 界面、叙事、存档与联机 | `game-ui-ux`、`dialogue-systems`、`save-systems`，以及当前引擎的 UI、网络与数据持久化技能 |
| 美术、模型、动画、特效与音频 | `create-game-assets`、`shader-programming`、`audio-design`，配合当前引擎的模型、动画、材质、着色器与音频技能；实际素材工具按任务另选 |
| 性能、测试、构建与交付 | `performance-optimization`、当前引擎的测试/导出/构建技能；目标渠道确为 Steam 或 itch.io 时再选 `steam-publish`、`itch-publish` |

未列出的新技能仍按实际描述与适用条件参与选择。组合使用是读取并应用相关技能的指导，不是把全部技能正文塞进上下文，也不代表每项游戏任务都要执行所有方法。

## 合并方法与处理冲突

- 引擎技能负责当前引擎的实现约束，玩法与系统技能补充领域方法，本体系负责选择、经验整理和交付。复用当前项目的状态所有者与接口，避免因多个技能各有模板而引入重复系统。
- 同一问题有多个建议时，根据项目实现、实际版本和可复现结果决定。技能中的示例版本、模板或固定数值不能直接替代项目约定；需要修改方案时说明适用条件与取舍。
- 跨引擎只迁移适用的设计或验证方法，API、生命周期、坐标和资源格式以当前引擎为准。不能把某引擎的方法未经验证写成跨引擎通则。
- 新安装技能用来解决实际问题。已有覆盖且验证有效的实现保持原方案；用户认可的手感、节奏、美术及可恢复基准按原约定保护。
- 选型入口与综合技能不反复相互路由；选定专项方法后进入实现。只执行当前任务授权的动作，构建、上传和发布分别判断。

## 总结、更新与修改

完成实际工作和必要验证后，按[自动维护规则](skill-maintenance.md)将经验归入本体系：

- **总结**：保留实际采用的方法、选择理由、验证结果与局限；被试验否定的方法应说明触发条件，避免下轮重复踩坑。
- **更新**：把有迁移价值的新方法写入相关参考，注明来源技能、适用引擎或条件与关键验证；新增方向较多时再建立对应参考文件并补上入口。
- **修改**：发现旧规则错误、过时或冲突时直接修正原条目，必要时删除已失效的指导，同时检查引用和适用范围。

保留来源技能的名称与定位方式即可，不整篇复制其文档。默认维护对象是“杨帆游戏开发体系”及必要入口；读取其他技能不等于修改它们。发现第三方技能问题时，可先在本体系记录经验证的适用边界；用户另行要求修改该技能时再按其维护约定处理。
