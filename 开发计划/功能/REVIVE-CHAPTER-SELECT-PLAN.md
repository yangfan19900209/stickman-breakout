# 原地复活、分享邀请与通关选关设计

> **2026-11-14 最新规则优先：** 用户明确“可以看10次视频，不是一次性给10个”。已改为每关每次挑战最多完整观看 10 条视频，每条领取 1 次原地复活机会，不叠加囤积；取消免费、分享和推荐领取复活。普通分享／推荐入口保留。见[视频复活方案](WECHAT-REWARDED-VIDEO-PLAN.md)及[本轮验证](../../开发进度/验证记录/rewarded-video-20261114/README.md)。

> **历史 2026-11-13 / 1.0.7 方案：** 首次免费 1 次及后续不限次数分享／推荐复活见[历史记录](../../开发进度/迭代记录/V107-SOCIAL-REVIVAL.md)，已被上方视频复活规则替代。下文保留原首版设计依据；通关、存档、安全落点和真机验收边界继续有效。

设计日期：2026-11-13，设计基于 1.0.4。P0 已按确认方案接入并形成 1.0.6 固定包，见[1.0.6 接入与验证](../../开发进度/迭代记录/V106-REVIVE-CHAPTER-SELECT.md)。配套 HTML 仍是独立设计原型，不是游戏运行入口。

## 1. 首版结论

建议做成「每关每次挑战可免费原地复活一次，失败页保留自愿分享邀请；通关第一关后可在首页选择关卡」。两关均支持复活。复活保留当前战场、武器弹药和 Boss 剩余血量，恢复 5 点生命、提供 3 秒保护；复活通关保存进度、解锁关卡，但不写入最快用时。

用户提出的「分享邀请可原地复活」不能在普通分享接口上可靠实现为「确认分享成功才发放复活」。因此首版建议将复活机会与是否分享分开；若必须让好友邀请带来额外复活，使用第 8 节的真实助力路线，不把打开分享面板或返回游戏当作发送成功。

可点击[流程原型](../原型/revive-chapter-select.html)，演示死亡、模拟分享/取消、一次复活、复活后结算、解锁和选关。原型使用示例战斗数据，不连接微信、不发送消息、不写游戏存档。

## 2. 微信能力与规则依据

2026-11-13 核验的[官方 API 类型定义](https://github.com/wechat-miniprogram/minigame-api-typings/blob/master/types/wx/lib.wx.api.d.ts)中，普通 `ShareAppMessageOption` 没有发送成功、取消回调，`shareAppMessage` 返回 `void`。由此不能据调用结束、`onShow`、后台停留时长或 shareTicket 认定邀请已经送达。继续使用 1.0.4 的同步主动调用和包内原画兜底。

当前[微信小程序平台运营规范](https://developers.weixin.qq.com/miniprogram/product/#滥用分享行为)页面标注最后编辑于 2026-11-03；2.5.1 限制强制分享、暗示分享及无需深度互动即可获得利益的分享，2.5.28 另有分享频率限制。该页亦包含小游戏特别规范。将「必须分享才能复活」或「分享返回立即奖励复活」直接作为默认发布流程，不适合作为本项目首版方案。这里不是认定所有好友活动都不可做：真实互动路线仍需结合活动规则和目标账号条件核验。

原始页面和核验记录保存在 `开发进度/验证记录/revive-select-design-20261113/`。本轮未核验微信账号后台能力，也未测试真实卡片收发。

## 3. 失败页与复活规则

失败页主按钮为「原地复活 · 剩余 1 次」，说明「满血继续 · 本局不计最快纪录」。次级按钮为「重玩本关」「返回首页」；「邀请朋友」独立放在下方，不加红点、闪烁、强制倒计时或自动弹分享。次数耗尽后主按钮换为「重玩本关」，展示「本次挑战的复活机会已使用」。

| 项目 | 首版确定规则 |
| --- | --- |
| 使用范围 | 第一关陆地、第二关水下；第三关仍关闭 |
| 次数 | 每关每次挑战 1 次；重玩、正式进入另一关开始新一轮，次数重置 |
| 消耗时机 | 安全位置确认、复活状态提交成功后消耗；连点只提交一次 |
| 生命 | 恢复到当前最大生命，现为 5 点 |
| 武器/弹药 | 保留死亡时当前武器、剩余弹药、手雷和背包状态；不补满弹药 |
| 战场 | 保留已击败敌人、Boss 血量/阶段、已破坏箱体、已领补给和地形变化 |
| 动态威胁 | 清除当前在途弹体、投掷物和待结算爆炸，不退款、不重复击杀；正在命中的持续攻击进入正常恢复，下一次攻击重新给完整预警 |
| 安全保护 | 恢复前短暂 1 秒准备提示，战场冻结；可操作时起算 3 秒无敌，暂停/后台不消耗 |
| 位置 | 优先死亡位置附近；危险或无支撑时回到同一遭遇段最近有效安全点，不重开整关 |
| 暂离 | 分享、后台、旋屏都停表并保持失败/准备状态；返回后由玩家点击继续，不自动复活 |
| 退出 | 首版不保存整场战斗快照；关闭游戏结束本次挑战，通关解锁与历史纪录照常保存 |

同帧死亡与击破 Boss 时遵守当前「玩家存活才结算胜利」条件。只在死亡流程结束后允许复活，不对过场、已胜利或章节加载状态发放复活。

### 安全落点与状态恢复

1. 正常游玩时按有限频率保存最后有效安全点。陆地要求真实支撑、完整站立净空、没有越过退让边界；水下要求整个人物不嵌入海床、船体、礁石或危险区域。
2. 复活时重新检查几何，不能直接信任历史点。移动平台应保存平台身份及局部位置，平台消失或当前位置无净空则放弃该点。
3. 顺序为死亡附近合法点、最近有效安全点、当前遭遇段的保底安全锚点；不得穿到未到达区域、越过 Boss 或退回已封锁区。没有合法位置时保持失败页，不扣次数，允许重试或重玩。
4. 清理死亡计时、受击/击退、速度、跳跃缓冲、冲刺、近战/投掷按压和残留触点；恢复合法朝向及姿态。水下保留装备完成和游泳阶段，不能重新播放悬崖入场。
5. 不调用整场 `reset()`：现有陆地 `GameSession.reset()` 会重置敌人、掉落和地图，`PlayerController.reset()` 会重置手雷和武器。应增加专用角色恢复与会话复活入口，水下恢复自己的武器、冷却和游动状态。

### 分享邀请

- 点「邀请朋友」直接调用现有微信分享；等待期间游戏仍冻结。取消、发送、外部返回都回到原失败页，复活次数不受影响。
- 卡片使用游戏原画与当前关卡，文案如「我在第 2 关深海突围，一起来挑战！」；不写「点一下救我」「已经帮好友复活」等没有实际效果的承诺。
- 普通邀请沿用 `from=progress&sv=1&rule=r1&level=2` 等现有协议。来访者遵守自己的解锁状态；未通第一关的玩家不会被邀请参数直接送到第二关。
- 无微信分享接口的 Web 版仍有免费复活；分享入口按现有平台能力显示。接口失败不扣次数、不阻断复活。

## 4. 已通关后的选关

首页主按钮随进度变化，避免继续挤压左下操作区，也与现有「推荐游戏」设计兼容：新玩家保留「开始突围」，通关第一关后改为「选择关卡」。分享、游戏圈和纪录榜的位置保持。

| 已保存进度 | 首页入口 | 第一关：废弃前哨站 | 第二关：深海突围 |
| --- | --- | --- | --- |
| 尚未通第一关 | 开始突围 | 可开始 | 锁定；先通关第一关 |
| 已通第一关 | 选择关卡 | 已通关，可重玩 | 已解锁，可继续挑战 |
| 已通两关 | 选择关卡 | 可重玩、刷纪录 | 可重玩、刷纪录 |

选关页只有两张卡片，显示关卡名、已解锁/已通关、本人最快纪录、进入按钮。复活通关但没有普通通关成绩时显示「已通关 · 暂无竞速纪录」。第三关不出现可点入口。第一次从第一关结算进入第二关的原流程保留，选关不是必经步骤。

- 使用 `PersonalRecords.records.cleared` 作为现有本机解锁依据；第一关始终可玩，第二关要求 `cleared >= 1`。`reached` 不能独立解锁，分享 query 也不能解锁。
- 正式选关是一局新的正式挑战，完整从关卡起点开始，使用该关标准装备/生命，不继承另一关剩余装备和复活次数；第二关保留现有入水流程及跳过规则。
- 资源先加载成功再提交会话。连点只加载一次，失败回到选关页并允许重试；后台或旋屏返回时不直接开始移动。
- 读取、判定和开始关卡都检查开放范围与本机进度，不能只禁用按钮。测试直达链接仍按调试流程处理，不能拿来实现正式选关或上传正式成绩。
- 老版本的合法本机通关记录直接生效，不重置 `r1` 最快纪录，不要求老玩家再打一遍。首版仍不提供跨设备本机存档恢复；云端好友榜有成绩不代表主域已读回解锁数据。

## 5. 个人纪录与排行榜

进度资格、竞速资格分开。每局在内存维护 `revivesUsed`、`assisted`；复活成功时将 `assisted` 设为真，此标记在本关内不可逆。关卡重开或进入下一关才重置。

| 场景 | 通关/解锁 | 本人最快与好友用时榜 |
| --- | --- | --- |
| 正常进入或合法选关，未复活通关 | 正常保存 | 合法时钟下可更新 |
| 使用复活后通关 | 正常保存，可进入下一关 | 不刷新；保留原最快纪录 |
| 第一关复活，第二关正常新局无复活 | 两关都可保存进度 | 第二关仍可独立刷新 |
| 调试直达、未解锁越关、异常时钟 | 沿现有调试/合法性约束 | 不产生正式最快成绩 |

复活前后累计可操作用时，不归零；死亡界面、分享、后台和恢复准备阶段不计入。结算展示「本局用时 X 秒 · 使用复活，不计最快纪录」。现有 `result.valid` 不再承担所有原因，需要明确 `timeEligible`/原因字段与进度资格；UI 不把复活局笼统显示为存档失败。只向云端提交进度及既有合格最佳，不提交复活局的新用时。分享复活通关用进度卡片，不能把该局耗时包装成竞速挑战；玩家仍可单独分享过去的合法最好成绩。

所有下列路径以当前整理后的 `源码/` 为工程根。下表 P0 已完成接入，实际验证与交付见上述迭代记录。

| 模块 | 计划改动 |

运行状态可采用 `playing → dying → gameover → reviving → playing`。只在 `gameover` 且有次数、当前会话仍有效时提交复活；准备阶段隐藏原生游戏圈、隔离键盘/触摸和其他弹层，按可暂停时间推进。重复生命周期通知、迟到分享返回和旧章节回调不改变新局。

## 7. 验收清单

1. 陆地与水下、普通战斗与 Boss 战均测试一次复活和第二次死亡；核对生命、装备、弹药、Boss 血量、已消耗补给和一次性掉落。
2. 空中被击败、坠落、低顶、平台消失、Boss 身体覆盖、海床/船体贴边，都不能复活即卡住或再次死亡；无合法点不扣次数。
3. 快速连点、分享取消/失败、分享后后台、重复 onShow、旋屏、重开后旧回调到达，都不能多领、自动续战或重新启动计时。
4. 复活局通关只更新进度，历史最快不丢失；普通重玩可刷新最快。第一关复活不污染第二关独立新局。
5. 全新存档、已通一关、已通两关、损坏/旧存档、存储失败、重新启动，核对选关状态和提示；失败存储不声称已永久保存。
6. 从选关进入两关、章节加载失败/后台、邀请指向锁定关、测试 URL 和第三关旧入口，统一检查资格。进入后全套正常输入可玩，通关可回首页再选关。
7. 小屏横屏、刘海、手势区、微信胶囊和竖屏处理；手机逻辑点击高度至少 44，按钮不拥挤，原生组件不覆盖新面板。
8. 逻辑测试、实际 Cocos 浏览器触控、两关正常输入回归、Web/微信构建分别验收；微信真机分享取消/发送、后台返回以及本机解锁保存单列，不用宿主模拟替代。

实施顺序：安全恢复与次数 → 纪录资格 → 失败页和分享 → 关卡资格与选关页 → 回归/构建。开始实现时建立新的可恢复基准，不覆盖 1.0.4 交付包或已认可的第一关锚点。

## 8. 后续：真实好友助力复活

若产品坚持「邀请产生复活收益」，需新增登录与后台，单独设计活动，而非给普通分享加一个 success 回调：

- 分享者主动创建带过期时间的助力单，绑定账号、关卡和唯一挑战；签名令牌放卡片，不放敏感身份或可信成绩。
- 好友打开后先看到完整规则，自愿参与与本游戏有关的实质互动，例如正常完成一段明确的试玩挑战。仅打开、等待数秒或自动回传不能作为方案默认的有效助力。
- 后台校验参与身份、非本人、活动有效期、一次性请求和助力/领取去重，再发可领取额度；主域只查询自己的助力结果，不读取好友开放数据数组。
- 分享者回来看到明确状态；没有完成有效助力时只能显示等待，不能假称失败要求反复分享。保留免费复活/重玩，不让当前战斗必须等好友上线。
- 助力完成不自动开始战斗。当前挑战已结束时不对新局发过期复活；若后续设计可存复活券，应另定义上限、有效期及存储，不与本首版次数混用。
- 此路线的规则、实际互动和账号可用性要另核验，后台验证只能证明事件发生，不代表平台自动认可活动设计。

首版推荐不接后台助力；先完成原地继续、关卡重玩和竞速公平这三个可独立验证的体验。
